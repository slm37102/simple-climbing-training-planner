# Grill queue

The **decision worklist**. Where `docs/improvement-backlog.md` (the `IB-*` ledger) is the full catalogue of everything the app should get better at, this file is the short, ordered list of items that are blocked on a **training-content decision** — the human-gated work that `/audit-loop` can find and file but structurally cannot build, because a change to prescription math must be decided (and reviewed) before it ships.

It exists because that work was the loop's dead end: `/audit-loop` drains the *engineering* backlog on its own, but every training item and every prescription-math trip-wire routes to the multi-session `/grill-with-docs → /to-spec → /to-tickets` path, and the first step of that path needs a live human. Rather than let those items sit as scattered "routed to multi-session" notes that never move, they collect here and get worked one at a time.

This is a lightweight, markdown-native cousin of the `/wayfinder` map: same philosophy (chart the decisions, resolve them one at a time until the way is clear), without the issue-tracker machinery. If this queue ever outgrows a flat list — real blocking edges, parallel sessions, fog that needs charting — graduate it to an actual `wayfinder:map` and retire this file.

## How to read this doc

- The queue below is **ordered by priority** (safety G3 > correctness G1/G2 > convenience > polish — the same order the backlog uses). The top unblocked row is the **frontier**: the next thing to grill.
- Each row is a **pointer**, not a write-up — the finding's detail lives in its `IB-*` backlog row and the source audit. The queue carries only: the ID, a one-line question, and status.
- This is **not a mirror of the training backlog.** Only items that are *ready to decide* live here. The rest stay in the backlog as the catalogue; `/audit-loop` and the user graduate them in as they rise to the frontier (wayfinder's "fog of war" — don't pre-slice what you can't yet phrase as a sharp question).
- **Status:** Queued / Grilling / Decided / Dropped.

## Coordination across sessions — the claim

Many sessions run at once (all yours), so a **claim** is what stops two of them grilling the same item. The claim lives on the **GitHub issue tracker**, not in this file — a markdown claim written on one session's branch is invisible to another until it merges, whereas an issue's comments are visible to every session instantly.

Every in-flight queue item is backed by a GitHub issue labelled **`grill-queue`**. Since every session is **you** (one GitHub user), an assignee would read the same on all of them, so it's skipped — the claim is simply a **comment**:

- **Claim = a `🔒 CLAIM` comment** naming your **Claude session id**, **branch**, and **UTC time**. An open `grill-queue` issue whose latest claim is an unresolved `🔒 CLAIM` is **taken**; one with no `🔒 CLAIM` (or only a stale one) is **free**.
- **Tiebreak:** right after commenting, re-read the issue; if an *earlier* `🔒 CLAIM` from a different session exists, **yield** and take the next item. Comment order is the lock.
- **Stale claims release.** A `🔒 CLAIM` with no follow-up for a few hours on a still-open issue is a dead session; reclaim it with a `♻️ RECLAIM` comment noting the takeover.

When an item is `Decided`, its issue is **closed** — off the board for everyone.

## How to work this queue — "run a grill section"

Invoke **`/grill-queue`** (or just say "grill the next item"). One item per session. The ritual follows `/grill-with-docs` = `/grilling` + `/domain-modeling`:

1. **Take the top claimable item** — the highest-priority `Queued` row whose issue is **open with no active `🔒 CLAIM`** (or the one the user names). **Claim it** per the section above (post a `🔒 CLAIM` comment; yield if an earlier claim exists). Then mark the row `Grilling`.
2. **Grill interactively — HITL.** Every open point is a `fact`, a `mechanism` or a `judgement`, and **only `judgement` reaches the user**: look **facts** up in the code and the `docs/` (training-philosophy, the ADRs, knowledge-gaps); **decide the mechanism yourself** and state the call (which module, which flag, what the regression pins); put the **judgement** — the training trade-off, the risk appetite, the scope — to the user and wait. The agent **never answers its own `judgement` question** — a grill where the agent supplies the human's side is broken. Write every round in the plain register from the first one (ASD-STE100 Simplified Technical English, the `CONTEXT.md` ubiquitous language, evidence and options carried in the question itself); `/wait-what` means a round missed it. Ground every branch in the evidence the way `docs/adr/` already does. Full rule: the `/grill-queue` skill.
3. **Produce a decision, not a deliverable.** The output of a grill is a settled call — what to build and why — not the code. Stop when there's shared understanding and nothing left to decide before someone builds it.
4. **Record it** (this is where a training finding **graduates**, per the repo convention):
   - Write the decision as a new **ADR** in `docs/adr/`, and add a **`KG-*`** row to `docs/knowledge-gaps.md` carrying the adjudicated verdict.
   - Mark the queue row **Decided**, linking the ADR.
   - Update the item's `IB-*` backlog row: it's now decided, so it's ready for the **build** path (`/to-spec → /to-tickets → PR`).
5. **Graduate fog.** If the decision makes a previously-vague backlog item phrasable as a sharp question, add it to the queue. If it reveals an item is out of scope, drop it (status `Dropped`, one-line why).

Grilling settles the *decision*; it does not ship code. Once an item is `Decided`, the build still runs as its own multi-session `/to-spec → /to-tickets` pass — but the hard, human-only part is done and captured durably.

- **IB-020** ([#77](https://github.com/slm37102/simple-climbing-training-planner/issues/77), 2026-08-09) — the limiter's finger comparison is duration-mismatched (10s benchmark vs 7s norm table). The issue offered three ways out; **two were eliminated before the judgement call, on evidence rather than preference.** *Retest at 7s* died on a code fact: `maxHang20mm` is `prescribeLoadKg`'s `baseMax` (`js/loads.js:78`) and ADR-0013 makes every phase band a percentage of total load built on it — the Peak comment even pegs the 7-53 load at "~97–100% of **the 10s max**" — so re-measuring at 7s would raise *every hangboard prescription* to fix an informational readout. **The 10s benchmark is fixed.** *Apply a conversion* died on a `/research` pass ([`max-hang-duration-norms.md`](research/max-hang-duration-norms.md)): there is **no peer-reviewed quantification of the 7s→10s delta at all**, so any factor would be a fresh invented constant — the exact posture ADR-0020 had just refused. That research also **overturned our own shipped reassurance**: `benchmark-norms.md` and `js/limiter.js:17-20` both told the reader the error was "bounded… a few percent of bodyweight" against the 6 pp threshold, but the only figures in circulation span **≈1–7 pp** — under one reading a *full grade step*, i.e. able to manufacture a clear verdict, not merely tip a borderline one. Decision: **settle now, and suppress the "limiter candidate" verdict** — state the comparison, withhold the conclusion, name the unquantified mismatch; correct the "bounded" claim to "direction known, magnitude unquantified"; keep the 10s benchmark and the Lattice table; **do not widen the threshold** (the amount to widen by is precisely the unknown). Suppression is deliberately *asymmetric*: the bias is one-directional and points at the only costly verdict (a false finger-limiter steers toward more finger volume — G3-expensive — when the likelier limiter is technique/tactics at ~17% R²), while the at-or-above and `elsewhere` lines are biased *against themselves* by the same error and so are left running. Declined the research agent's own "change nothing in `js/limiter.js`" — it predated weighing the 1–7 pp range against the 6 pp threshold, and a caveat under a possibly-artefactual verdict offloads the discounting onto the athlete. **Parking was rejected**: the correction holds whatever the table says. Clean exit queued as **IB-072** — Power Company Climbing is confirmed duration-matched (10s/20mm, unit convention pinned, converts cleanly) but every external host is 403-blocked by this environment's egress policy, so it is **blocked, not refuted**; if fetched it *replaces* the table and reverses the suppression. → [ADR-0011 addendum](adr/0011-limiter-readout.md), KG-B22. No schema/load-chain change (limiter is informational-only). Ready for `/to-spec → /to-tickets`.
- **IB-029** ([#75](https://github.com/slm37102/simple-climbing-training-planner/issues/75), 2026-08-09) — every autoregulation *magnitude* is an app-invented constant, and `js/loads.js:21-22`/`:46` **promise** a calibration loop ("Tune them from the athlete's own logs via KG-A4") that nothing implements. Two code facts reframed the question before it was answered: the whole chain governs only **~2 kg-bearing data points per week** (`prescribeLoadKg` returns null for every kind but `hangboard`/`pullup`, both on the single Monday session), and the RPE dead-band **already widens as RPE gets noisier** — monotonic band width 1.5 (Base pull-ups `[7,8.5]`) → 1.0 (hangs `[8,9]`) → 0.5 (Peak `[9,9.5]`), which *is* the tolerance-widening the audit asked for. Decision: **defaults are permanent, not a calibration backlog.** Self-tuning rejected on four grounds, strongest first: there is **no ground truth to fit against** (the outcome "the right load" is never observed; the only observable is next-session RPE, and `autoAdjust` already closes that loop — fitting the gain of a controller whose setpoint it already meets is circular); the data rate is disqualifying (~20 usable points/cycle, and the athlete's real history is thinner still); a fitted constant would **worsen the audit's actual complaint** (over-trust — it *reads* as earned while being less inspectable than "we made this up"); and ongoing complexity is a real "simple over clever" cost even though build time is not. The "surface, don't fit" middle option was the strongest challenger but its escalation path **largely already exists** (`rpeDriftSignal` → ADR-0012 micro-retest). One posture for all six constants, with the upward/downward **asymmetry recorded as rationale, not new mechanism**: the reward-upward three are bounded by `MAX_SESSION_PROGRESS` and suppressed on every hold (the ADR-0019 doctrine), the protective-downward three fail safe — so the honest claim is "guesses whose error is asymmetrically contained." The issue's **sub-maximal half was dissolved as a false premise**, not deferred: ARC (`kind:'arc'`) and 60/60 (`kind:'circuit'`) fall through `prescribeLoadKg`'s `else return null`, so the thermostat has never touched them and cannot; recorded like the IB-028 "retest is unreachable" finding so a future audit doesn't re-file it. **Permanent** (reopen only for new published research — more logs can't fix a missing outcome measure), **documents only** (reword the promise-comments; no constant moves, 0.5 kg step kept as a real-world plate quantum; a UI provenance surface was rejected as aggravating over-trust), and the **G3 tag retired** (P2 | G1 — the audit's own impact line says not injury). → [ADR-0020](adr/0020-autoregulation-magnitudes-are-permanent-conventions.md), KG-B21. **No build ticket** — the decision *is* the deliverable; only three comment rewordings in `js/loads.js` remain.
